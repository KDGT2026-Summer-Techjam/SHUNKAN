# Room中心の設計

## プロダクトの認識

旬間（SHUNKAN）は、個人用の期限付きRoom管理アプリです。利用者はユーザー登録・ログイン後、自分が所有するRoomだけを扱います。共有、公開、共同編集はMVP外です。

- 2026 夏は、2026-08-31 23:59:59 JSTを終了日時とするデモ用Roomです。
- TechJam 2026は、2026-08-28 18:00:00 JSTを終了日時とするデモ用Roomです。
- 文化祭まで、旅行までのように、利用者は目的ごとにRoomを作れます。
- Roomごとに開始日時・終了日時を持ち、カウントダウン、進捗、アルバムを独立して表示します。

```text
ログインした利用者
├─ 2026 夏
│  ├─ Category
│  ├─ Task
│  └─ MomentLogとPhoto
└─ TechJam 2026
   ├─ Category
   ├─ Task
   └─ MomentLogとPhoto
```

## データの関係

```text
User
└─ Room
   ├─ Category
   ├─ Task
   └─ MomentLog
      └─ Photo
```

| データ | 役割 | 例 |
| --- | --- | --- |
| Room | 期限とテーマをまとめる | 2026 夏、文化祭まで |
| Category | Room内での分類 | 花火、グルメ、準備 |
| Task | これからやりたいこと | 花火を見る |
| MomentLog | 実際に起きたこと・気持ちと、この瞬間へのひとこと | 最後の一発がすごかった |
| Photo | MomentLogに添える写真 | 花火の写真 |

完了Taskや進捗率は別テーブルにしない。Taskの完了状態と完了日時から、完了数と進捗率を計算する。

## 写真とこの瞬間へのひとこと

写真はTaskへ直接ぶら下げず、MomentLogに紐付ける。Taskの完了時には、任意でそのTaskに紐づくMomentLogを作成し、写真とこの瞬間へのひとことを残せる。

- MomentLogの本文は、出来事や気持ち、この瞬間へのひとことを1件だけ書く。
- Photoごとの`caption`は新規保存・表示・編集をしない。既存DB列は互換性のため残す。
- 写真はJPEG / PNG / WebP / GIF形式、1枚10MB以下、MomentLog 1件あたり最大3枚とする。
- 許可形式以外、壊れた画像、約4,000万画素を超える極端に大きな画像は保存しない。
- 保存時は元の縦横比を保って長辺1920px以下へ縮小・最適化し、GIFアニメーションは維持する。
- アルバムではCSSの`aspect-ratio: 1`と`object-fit: cover`により、中央基準で正方形かつ同じ大きさに統一表示する。保存ファイル自体を正方形には切り抜かない。


画像本体はDBではなくストレージに保存する。開発中はDjangoの`media/`、公開時は画像ストレージを使う。EXIFの撮影日時はMust完了後の対象とし、GPS・端末名などの生メタデータは明示的な同意なしに保存しない。

## Room状態と操作可否

| 状態 | Task | 通常SHUNKAN-log | Photo | Room設定 | 閲覧 |
| --- | --- | --- | --- | --- | --- |
| 開催中 | 作成・編集・削除・完了切替可 | 作成・編集・削除可 | 追加・削除可 | MVPで提供する操作だけ可 | 可 |
| 終了後・Additional未実装 | 不可 | 不可 | 不可 | 不可 | 可 |
| 振り返り期間・Additional実装時 | 不可 | 不可 | 不可 | 不可 | reflection新規投稿だけ可 |
| 振り返り期限後 | 不可 | 不可 | 不可 | 不可 | 可 |
| アーカイブ | 不可 | 不可 | 不可 | 不可 | 可 |

終了後は新規追加だけでなく、既存Taskの編集・削除・完了切替も不可とする。既存MomentLogとPhotoの編集・削除も不可とする。Room名、開始日時、終了日時などRoom設定の変更も不可とする。カテゴリの作成・編集・削除もTaskと同じく開催中のみ可とし、終了後は閲覧のみとする。

Additional実装時でも許可するのはreflectionの新規投稿だけである。Additional未実装時、終了済みRoomは閲覧専用とする。

Room状態の判定は複数画面に重複実装せず、一か所に集約する。UIで操作を隠すだけでなく、直接URLやPOSTでもサーバー側で拒否する。操作制御は[#59](https://github.com/KDGT2026-Summer-Techjam/SHUNKAN/issues/59)の方針に従う。

## DB制約の方針

PostgreSQLは開発・テストとも必須とし、SQLiteでの動作確認を完了条件にしない。

Room境界、Room期間、MomentLogあたりの写真3枚上限は、アプリケーションのフォーム・サービス層だけでなく、PostgreSQLのDBレベルでも守る方針とする。これにより、ORM以外の経路や並行した更新でも不正なデータを保存させない。詳細は[#60](https://github.com/KDGT2026-Summer-Techjam/SHUNKAN/issues/60)に従う。

## 画面遷移

```text
登録・ログイン
  ↓
Room一覧 ──→ Roomを作る
  ↓
Roomホーム
  ├─→ Task一覧 ──→ Task追加・編集 ──→ Task一覧
  ├─→ カテゴリ管理 ──→ Task一覧
  ├─→ 今を残す ──→ Room別アルバム
  └─→ Room別アルバム
```

各画面と更新エンドポイントは、Room所有者とRoom状態を共通の判定に通す。

## 実装の依存関係

1. PostgreSQL接続とRoom中心データモデル
2. ユーザー登録・ログイン・ログアウト、Room所有者制御
3. Room別URL、作成・切替、秒単位カウントダウン
4. Task、SHUNKAN-log、写真、Room別アルバム
5. Room状態の一元制御とPostgreSQLのDB制約
6. 権限・主要導線の結合テスト

実装の進捗・担当・完了状況はGitHub Issueを正本とする。AdditionalのreflectionとEXIFはMust完了後に扱う。
